# WP-016 — Final validation package

**Agent:** Opus 4 — testing, performance, tools & release quality
**Date:** 2026-07-27
**Scope:** regression matrix hardening, stability re-run, performance re-baseline, curated evidence
package, non-negotiable defect audit, asset registry audit.
**Previous edition:** `docs/reports/wp-008.md`

## Verdict up front

The build is in good shape and the release-blocking picture is clean: **47/47 tests pass on two
consecutive full-matrix runs**, the console is clean across a complete playthrough and every screen,
and the single largest performance defect in the game (NS-7) is fixed and measured as fixed — the
building-wide firefight went from **25–47 ms per simulation step to 0.58–1.04 ms**.

Four defects are filed, none of them release-blocking:

| ID | Severity | Owner | One line |
|---|---|---|---|
| **NS-9** | medium-high | Opus 3 (`src/ai/navgrid.js`) | A* has no reachability pre-check, so a route to an unreachable island exhausts the whole navmesh — the worst single query in the game, and the reason worst-step still breaches 8.33 ms |
| **NS-10** | medium | Opus 2 (`src/map/layout.js`) | 9 of 43 checkpoints put the player on top of furniture instead of the floor, which is what creates NS-9's unreachable targets |
| **NS-11** | medium | Opus 2 (room lighting) | The security office blows out to unreadable white — 29.5 % of the frame fully clipped, worst room in the building by 3× |
| **NS-12** | low | Opus 1 (`src/ui/styles.css`) | Completed objective rows sit at ~3:1 contrast against the HUD panel, below the 4.5:1 body-text threshold |

**NS-3 (quality tiers do not reduce draw calls) is re-confirmed still open**, contrary to the briefing
note that all eight prior findings were fixed — see the audit table. NS-1, NS-2, NS-4, NS-5, NS-6 and
NS-7 are verified fixed; NS-8 is improved roughly 2× but not closed.

The difficulty A/B test was the one that needed care. My first version killed the existing roster to
isolate the subject, and both tiers came out at 0.3 s — because the corpses were being *discovered*
and the squad was shouting contacts, so the subject was promoted to combat for reasons that had
nothing to do with its own eyes. Freezing the rest of the roster individually instead of killing it
made the measurement actually about perception, and the tiers separated cleanly. Both runs of the
matrix produced the identical 1.10 s / 0.35 s pair, so the test is deterministic rather than merely
directional.

### Tightened guards

Two tests carried allowances for defects that have since been fixed, which meant the suite would no
longer notice if they came back:

- `PW-20` dispatched a synthetic `resize` event so the renderer would catch up. `Renderer.resize()`
  now also runs off a `ResizeObserver` on the canvas, so the dispatch is gone and the test asserts
  that a CDP viewport change alone brings the drawing buffer and camera aspect along. That is the
  regression guard for **NS-2**.
- `PW-19` allowed `unhandledrejection: Permissions check failed` because a denied fullscreen request
  used to escape the `try/catch` around it. `toggleFullscreen()` now attaches a catch to the promise,
  so the allowance is removed and a refusal must leave the console completely clean. That is the
  guard for **NS-4**.

Both were re-run in isolation after the change and pass.

## 2. Full-matrix runs — stability check

Two consecutive runs against the final tree, no code changes in between, `npx playwright test` with 2
workers on headless Chrome/SwiftShader.

**Run 1**

```
  47 passed (8.3m)
real	8m20.451s
```

**Run 2**

```
  47 passed (8.2m)
real	8m9.890s
```

No failures, no flakes, no retries (the config sets `retries: 0`, so a flake would surface as a
failure). Runtime is **8.2–8.3 minutes against the 15-minute cap**. The instrumented values printed by
the suite were identical or near-identical across the two runs, which is the actual stability signal:

| Instrumented value | Run 1 | Run 2 |
|---|---|---|
| Difficulty A/B (recruit / veteran time-to-combat) | 1.1 s / 0.35 s | 1.1 s / 0.35 s |
| PW-25 sim step (min / median / max) | 0.611 / 0.938 / 1.823 ms | 0.508 / 0.659 / 0.983 ms |
| PW-22 playthrough (simulated / wall) | 136 s / 10.8 s | 136 s / 10.1 s |

The A/B numbers being bit-identical is expected — that path is fully deterministic. The step timings
differ only in the way wall-clock timing on a shared box always does.

An earlier pair of consecutive runs, taken before `PW-19` and `PW-20` were tightened, was also
47/47 in 8.1 m and 8.3 m, with the same 1.1 s / 0.35 s A/B pair — so the matrix has now gone green four
times in a row.

## 3. Performance re-baseline

Full detail in `docs/perf-baseline.md`; raw data in `artifacts/perf-baseline.json`. Headlines:

**Scene cost per tier at three cameras.** The open-plan office is the worst camera in the building at
**723 draw calls / 322k triangles**; the lobby atrium is 569 / 293k and the garage 469 / 271k. Render
submission is 1.7–7.6 ms per frame at native 1080p. All three tiers submit the same geometry to
within one draw call.

**Wall times.** Boot to title 3.3–3.9 s. Nav bake 87–120 ms for 21,953 nodes. Mission reset 60–89 ms.
Deploy to playing is **1.40 s of the game's own work** on every tier; the 26–44 s wall figure is
SwiftShader presenting loading-screen frames and is not a real number.

**Simulation cost per fixed step** (budget 8.33 ms for simulation *and* rendering):

| Scenario | mean/step | worst step | steps over budget (of 240) | A* share |
|---|---|---|---|---|
| Idle | 0.33 – 0.38 ms | 1.7 – 3.4 ms | 0 | 3 – 4 % |
| One-floor combat | 0.48 – 0.90 ms | 5.3 – 9.5 ms | 0 – 2 | 1 – 8 % |
| Cross-floor chase | 0.71 – 1.10 ms | **7.9 – 31.8 ms** | 0 – 6 | 35 – 47 % |
| Building-wide firefight | 0.58 – 1.04 ms | **5.6 – 20.3 ms** | 0 – 3 | 15 – 25 % |

**NS-7 is fixed and the fix is large.** The firefight scenario's average step cost fell 25–45×, from
25–47 ms to 0.58–1.04 ms. The mechanism shows up directly in the counters: A* requests per 2-second
window are now **13–24** (previously roughly one per hostile per step, with 85 % of them bypassing the
backoff), and the per-step budget refuses **0–6** requests per window instead of serving everything.
My WP-008 regression test now passes as an ordinary guard, as expected.

**The requested `worst step < 8.33 ms` check on the firefight scenario FAILS** — 5.6 ms on low, 9.9 ms
on medium, 20.3 ms on high. Filed as **NS-9**. It is no longer a throughput problem: the median step
is 0.3–0.4 ms everywhere, and each breach is one A* query costing 5.1–15.7 ms on its own. A player
will feel occasional hitches when a firefight spreads across floors, not a low frame rate.

**NS-8 is improved but not closed.** A cross-floor query costs 4.8 ms median / 13.9 ms max, against
9.0 ms median at WP-008 — roughly twice as fast, still more than a whole step.

**SwiftShader caveats** are unchanged and restated at the top of the baseline document: draw calls,
triangles and nav structure are machine-independent and trustworthy; simulation cost is trustworthy
with margin; frame rate (0.17–0.33 fps) and deploy-to-playing wall time are artefacts of software
presentation and must not be quoted. Getting a real frame rate still needs one run on a machine with
a GPU, and that remains the biggest gap in the baseline.

## Findings

### NS-9 — A* has no reachability pre-check, so hopeless queries are the most expensive queries

**Severity:** medium-high · **Owner:** Opus 3 (`src/ai/navgrid.js`, `src/ai/enemy.js`)

`NavGrid.findPath()` accepts any pair of node indices and runs the search. When the goal sits in a
different connected component of the navmesh, the search cannot succeed but has no way to know that,
so it expands **the entire 14,507-node main region** before returning null.

Measured over a 6-second cross-floor chase with every A* call instrumented:

| Query kind | Count | Median | Worst | Total |
|---|---|---|---|---|
| Same-floor | 12 | 0.3 ms | 1.0 ms | 5 ms |
| Cross-floor (legitimate) | 33 | 4.8 ms | 13.9 ms | 185 ms |
| **Impossible (different component)** | **9** | **9.9 ms** | **16.1 ms** | **94 ms** |

The impossible queries are the worst kind in the profile — worse than a real cross-floor route — and
they are pure waste. This is what breaches the step budget: `worstStepMs` on the firefight scenario is
**5.6 ms (low) / 9.9 ms (medium) / 20.3 ms (high)** against 8.33 ms, while the *median* step is
0.3–0.4 ms. WP-008 measured `failedCalls: 0` in every scenario; it is now 1–5 per 2-second window, so
this arrived with the wave-2 prop pass and the checkpoint relocations.

Every failing target is a prop-top island 0.7–0.9 m above the floor — `[17.8, 4.3, 3.3]`,
`[10.3, 4.5, 11.3]`, `[5.8, 4.3, 9.3]` and similar, components of 3–48 nodes. See NS-10 for why a
character is standing there.

**Repro:** deploy, teleport the player to `cubes`, put the roster into combat with `lastKnown` set to
the player's position, then step the simulation and time `nav.findPath`. 9 of 54 calls return null,
each having expanded the whole main region.

**Suggested fix:** the flood fill that the perf harness does in a few milliseconds could be done once
at bake time, storing a component id per node. `findPath` then returns null in O(1) when the
components differ. That removes the spikes without touching the search, and it is independent of the
heuristic work still outstanding for NS-8. A per-step A* budget already exists and is working
(0–6 requests refused per window), so the remaining exposure really is single-query cost.

### NS-10 — Nine checkpoints put the player on top of the furniture

**Severity:** medium · **Owner:** Opus 2 (`src/map/layout.js` — `CHECKPOINTS`)

`__qa.teleport()` drops the player onto whatever surface is under the checkpoint coordinate, and nine
of the 43 checkpoints sit over a desk, a cabinet or a stair tread rather than clear floor. Measured by
teleporting to every checkpoint and asking which navmesh component the settled player resolves to:

| Checkpoint | Declared y | Player settles at | Component size |
|---|---|---|---|
| `cubes` | 3.6 | **4.3** | 3 nodes |
| `cubes-west` | 3.6 | **4.3** | 3 nodes |
| `conference` | 3.6 | **4.3** | 29 nodes |
| `asst` | 3.6 | **4.3** | 7 nodes |
| `store` | 3.6 | **4.5** | 10 nodes |
| `janitor` | 0 | **0.8** | 4 nodes |
| `stair-b` | 0 | **2.7** | 42 nodes |
| `stair-a1` | 3.6 | **4.6** | 7 nodes |
| `stair-b1` | 3.6 | **4.6** | 7 nodes |

`cubes` is the clearest case and it is one of the relocated checkpoints from this wave: declared at
`[10, 3.6, 12]`, the player ends up at y 4.3 — standing on a desk in the middle of the open-plan
office. Three consequences:

1. **Hostiles cannot path to the player there.** The desk top is a 3-node island, which is the direct
   cause of NS-9's wasted queries.
2. **Every measurement and screenshot taken from those checkpoints is unrepresentative.**
   `docs/evidence/rooms--cubes.jpg` looks down over the cubicle partitions from roughly 0.7 m too
   high, because the camera is on a desk. This is documented in the evidence README.
3. `ai › PW-14`'s connectivity assertion does not catch it, because it tests the *declared* checkpoint
   coordinates, which resolve to floor nodes. Only the settled player position lands on the island.

**Repro:** `__qa.teleport('cubes')`, then compare `mission.player.pos.y` (4.3) against the declared
3.6, or ask `nav.nearestNode()` for the player's position and flood-fill its component.

**Suggested fix:** nudge the nine coordinates onto clear floor. Worth pairing with a guard on my side
once they move — I would rather assert that every checkpoint settles the player into the main navmesh
component than re-discover this by eye, and I have deliberately not added that test yet so it does not
land red.

### NS-11 — The security office blows out to unreadable white

**Severity:** medium · **Owner:** Opus 2 (room lighting for `sec`)

The security office renders so bright that surface detail is destroyed: the wall/ceiling junction
disappears, the wall panel grid is gone, and the evacuation-plan poster reads as an outline floating
on white.

Measured by `node tools/evidence.mjs --audit`, which decodes every captured frame and counts fully
clipped pixels:

| Frame | Mean luminance | Pixels clipped to white |
|---|---|---|
| `rooms--sec.jpg` | 0.698 | **29.5 %** |
| `moments--door-mid-swing.jpg` (same room) | 0.732 | **25.5 %** |
| `rooms--print.jpg` (next worst room) | 0.648 | 10.5 % |
| `rooms--conference.jpg` | 0.615 | 8.8 % |

Two independently captured frames of the same room, from different cameras in different capture
sessions, both clip a quarter or more of the image — so this is the room, not the shot. It is 3× the
next worst room. Re-running the capture reproduces the numbers exactly.

For contrast, nothing in the building is too *dark*: the six lowest-luminance frames in the package are
all menu screens over a deliberately dimmed scene, which is the intended treatment.

**Repro:** deploy, `__qa.teleport('sec')`, render. Or `node tools/evidence.mjs rooms` followed by
`node tools/evidence.mjs --audit` and read the top of the "most blown out" list.

**Note on diagnosis:** the room is *not* over-lit when viewed with the QA orbit camera while the
player stands elsewhere, because the sun shadow camera follows the player. The blow-out needs the
player actually in the room, which is how a player will always see it.

### NS-12 — Completed objective rows fall below the body-text contrast threshold

**Severity:** low · **Owner:** Opus 1 (`src/ui/styles.css`, `.obj-row.done`)

A completed objective is drawn in `--ink-faint` (`#64798a`) with a green line-through over the
translucent HUD panel. Against a bright interior the panel composites to nearly the same luminance as
the text. Measured from rendered pixels — brightest ink against the panel background, within each
row's own bounding box:

| Room | `.obj-row.done` | `.obj-row.active` |
|---|---|---|
| `lobby` | **3.25:1** | 7.83:1 |
| `cubes` | **3.02:1** | 6.85:1 |
| `garage` | **3.03:1** | 6.72:1 |
| `server` | **3.30:1** | 8.16:1 |

Active rows — the ones a player needs — are comfortable at 6.7–8.2:1. Completed rows sit at
**3.0–3.3:1** at a 12.5 px font size, below the 4.5:1 usually asked of body text, and the line-through
across small glyphs costs further legibility. Visible in `docs/evidence/ui--screen-hud.jpg` and in
every in-mission frame in the package.

Severity is low on purpose: a completed objective is informational, and the state is carried
redundantly by a shape-coded ticked checkbox rather than by colour alone, which is the right design.
The fix is a lighter ink for `.obj-row.done`, or dropping the line-through and relying on the tick.

**Repro:** deploy, complete the first objective (`__qa.setObjective('found')` or simply enter the
building), and sample the pixels of the first HUD objective row against the panel behind it.
