### Coverage that is deliberately partial

- **PW-19 fullscreen (partial).** Headless Chrome will not grant fullscreen for a synthesised key
  event, so the test verifies that `F` reaches the handler and that a refusal leaves the mission
  running. Entering fullscreen and leaving it with Esc needs a real browser session and is not
  covered. The refusal path did surface a bug — NS-4.
- **Pointer lock (not covered).** Real pointer lock needs a user gesture headless cannot produce.
  All look input goes through `__qa.look()`, which is the same code path `Input.snapshot()` consumes.
- **Audio (not covered).** Volumes are pinned to 0 in the harness. Nothing asserts audible output.
- **Visual correctness (not covered).** No screenshot comparison: SwiftShader output is not stable
  enough between runs to diff, and `tools/capture*.js` already covers art review.

### NS-1 — The navmesh was split into disconnected regions; the two floors did not join — **FIXED**
**Severity was: high (functional + performance).** Owner: **Opus 3** (`src/ai/navgrid.js`), with
**Fable 2** for the stair geometry. Verified fixed 2026-07-26T13:37Z; kept here because the
regression test and the previous baseline both refer to it.

Earlier in this work package a flood fill over the baked graph found the two floors in separate
regions — 14,579 nodes and 6,744 nodes — so no hostile could path up or down the stairs, and every
cross-floor request became an exhaustive 22,002-node search that returned `null`.

The map work since then joined them. Confirmed by four independent checks: `__qa.navConnected` between
lobby and conference returns `connected: true`; a route from the lobby to **each of the 30 checkpoints
in `src/map/layout.js`** resolves; `unreachableCalls` and `failedCalls` are **0** across every
scenario in `tools/perf-baseline.mjs`; and all 14 hostiles now bake into the same region. Region 0
holds 14,579 nodes and covers both floors, the stairwells and the exterior. The remaining 112 regions
are the roof (6,744 nodes at y ≈ 6.7, which nothing is asked to walk to) and 110 pockets under 50
nodes on prop tops and ledges.

`ai › PW-14 the navmesh is a connected whole so hostiles can chase between floors` is now an ordinary
passing test and guards all of the above, including a bound on island size so a room can never get
sealed off unnoticed.

**The performance problem did not go away with it** — it changed shape, and is now NS-7 and NS-8
below. Cross-floor routes are found, but they are expensive, and they are requested far too often.

### NS-7 — A hostile whose move is clamped re-paths on *every* sim step
**Severity: high (performance).** Owner: **Opus 3** (`src/ai/enemy.js`).

This is the largest single performance defect in the game right now: **one hostile can spend 74 % of
the wall time of a simulation window on its own pathfinding.**

The re-path guard is:

```js
if (!this.path || this.repathT <= 0) {
  this.path = this.mission.findPath(this.pos, wantMove);
  this.pathIdx = 0;
  this.repathT = 0.9 + rng.next() * 0.7;   // intended: ask again in 0.9-1.6 s
}
```

and the mover's safety net, ~20 lines below, is:

```js
if (jump > 0.5) {
  // safety net: never accept a clamp-teleport; repath instead
  this.path = null;
  this.repathT = 0.2;
}
```

The safety net sets a 0.2 s backoff and nulls the path in the same breath, but `!this.path` is the
*first* arm of the guard, so it fires on the very next step and the backoff it just set is never read.
A hostile whose mover keeps clamping therefore asks for a fresh route on nearly every step — up to 120
a second, 76 measured. The same bypass applies to the `this.path = null` at the end of the waypoint
walk.

Measured during a cross-floor chase, 14 hostiles, 4 simulated seconds:

| | Measured | By design |
|---|---|---|
| Requests per hostile per second, mean | **6.84** | ~0.8 |
| Requests per second, worst hostile (`e-lobby-2`) | **76.3** | ~0.8 |
| Requests issued while `repathT` was still positive | **85.4 %** | 0 % |
| Wall time in that one hostile's A* | **1,592 ms of 2,155 ms (74 %)** | — |
| Requests that failed | 0 | — |

The signature is unmistakable in the samples: `repathT` reads exactly `0.192` — 0.2 minus one step —
on call after call, and every call returns a valid 31-waypoint route. Nothing is wrong with the
navmesh or the search result; the hostile is simply throwing the answer away and asking again.

Reproduce:
```bash
npx playwright test tests/systems.spec.js -g "re-path backoff"
```
Annotated `test.fail()` so the suite stays green while the bug is open; when it is fixed the test
reports "expected to fail but passed", which is the signal to drop the annotation. The test asserts
under 4 requests per second for the worst hostile and under 2 on average.

Two things to consider when fixing. The guard needs the timer to have the last word — letting
`repathT` gate both arms, with an explicit "ask now" flag for the cases that genuinely cannot wait
(a fresh alert, arriving at a patrol waypoint), keeps the safety net's own backoff meaningful.
Separately, it is worth asking why `e-lobby-2` clamps on nearly every step to begin with: a hostile
that cannot follow the route it was just given is a movement bug as well as a performance one, and
the pathfinding cost is only how it became visible.

### NS-8 — A cross-floor A* query costs ~9 ms, more than a whole fixed step
**Severity: medium-high (performance).** Owner: **Opus 3** (`src/ai/navgrid.js`).

Even at the intended re-path rate, cross-floor routing is too expensive to be called from the
simulation without a budget:

| Query | Median | Worst observed |
|---|---|---|
| Lobby → conference (floor 1 → floor 2) | **9.0 ms** | 41 ms |
| Same floor, comparable distance | **0.16 ms** | — |

The fixed step is 1/120 s, so **a single cross-floor query can exceed the entire 8.33 ms step
budget**. The cause is the heuristic in `NavGrid.findPath`:

```js
const h = (i) => {
  const n = this.nodes[i];
  return Math.hypot(n.x - target.x, n.z - target.z) + Math.abs(n.y - target.y) * 2;
};
```

Straight-line XZ distance plus a doubled height term points the search at the column below or above
the target, not at the stairwell that actually reaches it, so A* expands a large fraction of the
22,002-node graph before it commits to the detour. With the roster alerted to a position on the other
floor, the simulation spends **88–91 % of every step in A*** at 5.7–10.9 ms per step; in a firefight
that wakes the whole building it is **97 % at 25–47 ms per step**.

Reproduce:
```bash
npx vite --port 5187 --strictPort
node tools/perf-baseline.mjs --tiers high    # tiers.high.sim.crossFloor / .vfx
```

Worth considering: a hierarchical graph (portal or per-floor with stairwell links) so the search is
two cheap queries instead of one expensive one; caching a route per (region pair, target cell); and a
per-frame A* budget so at most one or two hostiles re-path in any given step, which also caps the
worst case regardless of the heuristic. NS-7 should be fixed first — it is a two-line change and it
removes roughly an order of magnitude of the requests that make this visible.

### NS-2 — `Renderer.resize()` only reacts to the window `resize` event
**Severity: medium.** Owner: **Opus 1** (`src/core/renderer.js`).

The canvas is CSS-sized to the viewport, but the drawing buffer and `camera.aspect` are updated only
from a `window` `resize` listener. Any viewport change that does not raise that event leaves the
buffer and the camera aspect stale, and the canvas is stretched to the new CSS size — a visibly
distorted, wrong-aspect image.

This reproduces immediately under Playwright, which changes the viewport through CDP metric
overrides: `window.innerWidth` updates, the page re-lays out, the canvas CSS size follows, and no
`resize` event fires. Observed at 1920×1080 → 1366×768: `innerWidth` 1366, canvas CSS 1366×768,
drawing buffer still 960×540, `renderer.width` still 1920, five seconds later unchanged.

`tests/boot.spec.js` dispatches a synthetic `resize` after each viewport change and says why in a
comment. A `ResizeObserver` on the canvas would make this robust regardless of how the size changed.

Reproduce: `npx playwright test tests/boot.spec.js -g "resize"` after removing the
`window.dispatchEvent(new Event('resize'))` line from the `resizeTo` helper.

### NS-3 — Quality tiers do not reduce the draw-call count
**Severity: medium (design).** Owner: **Opus 1** (`QUALITY` in `src/core/renderer.js`), with
**Fable 3** for prop LOD.

`low`, `medium`, `high` and `ultra` differ only in shadow-map size, fill-light budget, particle
scale, anisotropy and pixel-ratio cap. Draw calls and triangles are identical across tiers:
**810–811 calls, 296,628 triangles** at 1080p in the lobby. Measured software render time varies by
less than run-to-run noise between tiers.

So a player on weak hardware gets a smaller shadow map and fewer lights but still pays for all 810
draw calls, which is the cost most likely to bind on a low-end CPU. If tiers are meant to be a real
performance lever they need to reach geometry submission — instancing, merging static geometry, or
prop tiers. See `docs/perf-baseline.md` for the full table.

### NS-4 — `toggleFullscreen()` leaks an unhandled promise rejection
**Severity: low.** Owner: **Opus 1** (`src/game/game.js`).

```js
try {
  if (document.fullscreenElement) document.exitFullscreen();
  else document.documentElement.requestFullscreen();
} catch { /* headless */ }
```

`requestFullscreen()` rejects *asynchronously*, so the `try/catch` never sees it and the refusal
escapes as `unhandledrejection: TypeError: Permissions check failed`. Any environment that refuses
fullscreen — no user gesture, a permissions policy, an embedded frame — produces a console error on
every press of `F`. A `.catch(() => {})` on both calls closes it.

Reproduce: `npx playwright test tests/mission.spec.js -g "fullscreen"`, then read
`window.__consoleErrors`. The test currently allows exactly this message and cites this entry.

### NS-5 — `__qa.selectSlot()` reports the slot that is live, not the one requested
**Severity: low (QA surface).** Owner: **Opus 4** (`src/core/qa.js`, mine by delegation — not
touched during this work package, which was test-only).

`selectSlot(n)` calls `arsenal.trySwitch(n)` and returns `arsenal.active`, but the switch has to
holster and draw first, so the return value is the *previous* slot. `__qa.selectSlot(1)` returning
`2` reads like a rejected request when the switch is in fact under way. Returning the requested
slot, or `{ requested, active }`, would make it usable for automation. `tests/systems.spec.js`
asserts on the equipped slot after the draw completes instead.

### NS-6 — `god` and `noclip` survive a mission reset
**Severity: low (QA surface).** Owner: **Opus 2** (`src/player/player.js`) / **Opus 4**.

`Mission.reset()` calls `player.spawn()`, which restores `health`, `armor` and `alive` but leaves
`godMode` and `noclip` as they were, because both are only initialised in the constructor. A QA
session that enables god mode and then restarts silently keeps it, which is a good way to make a
later observation meaningless. The harness works around it by setting `god` explicitly on every
`quickStart`.

## 4. Performance summary

Full detail and caveats in `docs/perf-baseline.md`. The short version:

- **Frame rate is not measured.** Headless SwiftShader spends around a second *presenting* each
  frame, outside the engine's own timers, which pins the reported figure at 0.4–0.6 fps regardless
  of quality. That number is an artefact. The renderer's own draw is **2.5–15 ms at native 1080p**,
  which is encouraging but says nothing definitive about a GPU. A run on real hardware is the
  biggest outstanding gap.
- **Scene cost:** 810–811 draw calls, 296,628 triangles, 12–13 shader programs, 747–748 geometries,
  79 textures. Identical across quality tiers (NS-3).
- **Simulation, against an 8.33 ms fixed-step budget:** 0.33–0.47 ms idle, 0.54–1.03 ms with the
  roster in combat on one floor, **5.7–10.9 ms when hostiles chase across floors**, and **25–47 ms in
  a firefight that wakes the building** — 97 % of it in A* (NS-7, NS-8).
- **VFX are cheap.** `Particles.update()` costs 0.135–0.362 ms per call, 0.2–2.8 % of a heavy window,
  carrying 56–94 live particles plus three smoke volumes. Nothing to do here.
- **Load times:** boot to title 3.0–4.6 s, nav bake 95–204 ms for 22,002 nodes, mission reset
  82–148 ms.
- **Will it hold 60 fps on a mid GPU?** Rendering, probably — unproven. Simulation, not during a
  building-wide firefight. That is now purely a pathfinding problem, and NS-7 is a two-line fix that
  should remove most of it.

## 5. Notes on how the suite gets its determinism and its speed

Three decisions in `tests/helpers/game.js` are worth knowing about, because they are not obvious and
they are what make the suite both reproducible and fast enough to be useful.

**The RAF loop is stopped after boot, and one manual step is taken first.** Until `advanceTime()` is
called the engine is still stepping the simulation from real elapsed time, so anything observed
between entering a mission and the first `advanceTime()` depended on how busy the machine was — that
was a real source of flakiness, and it is why an early patrol test saw `patrol-wait` instead of
`patrol`. One `advanceTime(1)` puts the engine in manual mode for good.

**Rendering is on demand.** `Engine.advance()` renders a frame at the end of every `advanceTime()`
call. A frame drawn as the only work in an event-loop task costs 5–15 s here, while the same frames
drawn back to back inside one task cost about 30 ms each — a 300× difference, and the reason a spec
that steps time forty times used to spend minutes presenting frames nobody looks at. So
`advanceTime()` no longer renders, `renderInfo()` draws one frame before reading renderer
statistics, and `expectNoErrors()` draws one at the end of every test, which keeps the render path
exercised in every spec. Specs that are *about* rendering pass `render: 'always'`. This took the
suite from roughly 40 minutes to under 10, against a 15-minute target.

**Settings are seeded once per browser context, not once per navigation.** The harness writes the
test settings into `localStorage` from an init script, and an init script runs again on
`page.reload()` — which quietly re-seeded the defaults on top of whatever the game had persisted, so
the settings-persistence test was asserting against its own harness rather than against the game. A
marker key makes the seed happen only on the first navigation of each context.

**Vite's HMR client is stubbed per page.** Several agents edit `src/**` while this suite runs, and a
hot update to a module without an accept handler makes Vite reload the page, which destroys the
execution context mid-test. The stub keeps module loading intact and removes only live reload. Before
this, tests failed with `Execution context was destroyed` and misleading module-export errors.

One allowance exists in the console assertions: the NS-4 unhandled rejection, in the fullscreen test
only. `expectNoErrors(game, label, { allow: [...] })` takes regexes and every use cites a finding
here, so an allowance cannot quietly become permanent.
